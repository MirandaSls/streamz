# Contrato de configuração do Streamz no celular

Este arquivo é curto de propósito. Ele registra as **decisões de configuração**
que Android (PR do Bloco 2) e iOS (PR do Bloco 3) têm que respeitar para não
divergirem, e o porquê de cada uma. Quem quiser o passo a passo de compra,
pipeline e limitações vai em `docs/APPS-MOBILE.md`; quem quiser o release do
desktop vai no §5 de `docs/PROCESSO-DE-DESENVOLVIMENTO.md`.

## 1. Um crate só, três plataformas

Android e iOS **reaproveitam `apps/desktop/src-tauri`**. Não há `apps/mobile`,
não há segundo `Cargo.toml`, não há segundo `frontendDist` — é o mesmo
`../../web/out` que o Windows empacota. Motivo: o produto é o mesmo app; um
crate por plataforma significaria manter três cópias do `main.rs`, das
`capabilities/` e da CSP, e a primeira divergência apareceria num bug de
produção, não numa revisão.

Consequência obrigatória: o crate vira **lib + bin**.

```toml
[lib]
name = "streamz_desktop_lib"
crate-type = ["staticlib", "cdylib", "rlib"]
```

`src/lib.rs` recebe o corpo do `main.rs` de hoje dentro de
`#[cfg_attr(mobile, tauri::mobile_entry_point)] pub fn run()`, e `src/main.rs`
fica sendo só `streamz_desktop_lib::run()`. No Android e no iOS **não existe
`main()`**: o sistema carrega a biblioteca e chama esse ponto de entrada. O
desktop continua idêntico — mesmo código, mesmo binário, só mudou de arquivo.
Essa refatoração é entregue no **PR do Bloco 2**.

O bloco `[target.'cfg(windows)'.dependencies]` (webview2-com, windows-capture,
livekit, image, base64) e o `src/tela/` continuam **só do Windows**. Nada disso
compila para Android/iOS, e nada disso deve deixar de estar sob `cfg`.

## 2. Config por plataforma: arquivos irmãos, merge patch

A configuração específica de cada celular mora ao lado do `tauri.conf.json`:

- `apps/desktop/src-tauri/tauri.android.conf.json`
- `apps/desktop/src-tauri/tauri.ios.conf.json`

O Tauri mescla por **JSON Merge Patch (RFC 7396)**: objetos mesclam chave a
chave, **arrays substituem o array inteiro** — inclusive `app.windows`. Ao
redefinir `app.windows` no arquivo de plataforma é preciso **repetir tudo** que
se quer manter; o que for omitido cai no *default* do Tauri, não no valor do
arquivo base. É exatamente esse comportamento que se usa aqui: o celular
descarta as duas janelas do desktop de uma vez.

Duas coisas do desktop **não valem** no celular e é o arquivo de plataforma que
as remove:

- `decorations: false` + a nossa barra de título (`BarraDeTituloMinima`). No
  celular não há barra de título para substituir.
- a janela `splash` de 300×350. Ela existe para a checagem de atualização do
  updater do Tauri, que **não cobre Android nem iOS** (§4).

## 3. Identificadores

| | |
|---|---|
| desktop (Windows) | `dev.streamz.app` — já publicado, **não muda** |
| iOS | `chat.streamz.app` |
| Android | decidido no PR do Bloco 2; uma vez publicado na Play, **não muda nunca mais** |

O `identifier` do iOS vem no `tauri.ios.conf.json`. Trocar o identificador de um
app já publicado equivale a publicar um app novo — por isso o desktop fica onde
está, mesmo destoando.

O `versionCode` do Android é derivado da versão semântica
(`major*1000000 + minor*1000 + patch`) e o `bundleVersion` do iOS é o
equivalente do lado da Apple. Os dois entram na mesma leva de bump do §5 do
processo, que hoje toca quatro arquivos
(`apps/desktop/package.json`, `tauri.conf.json`, `Cargo.toml`, `Cargo.lock`).

## 4. Capacidades (`capabilities/`)

O campo `platforms` aceita exatamente `"windows"`, `"linux"`, `"macOS"`,
`"android"`, `"iOS"`. Quando ausente, vale para todas — e é isso que quebra o
`android init`, porque `default.json` e `splash.json` pedem permissões que só
existem no desktop (`core:window:allow-toggle-maximize`, `start-dragging`,
bandeja, `updater`).

Divisão acordada:

| arquivo | `platforms` | dono |
|---|---|---|
| `capabilities/default.json` | `["windows","linux","macOS"]` | Bloco 2 |
| `capabilities/splash.json` | `["windows","linux","macOS"]` | Bloco 2 |
| `capabilities/mobile.json` | `["android","iOS"]` | Bloco 2 |
| `capabilities/ios.json` | `["iOS"]` | Bloco 3 |

Os nomes de permissão **se conferem na versão presa no `Cargo.lock`**
(`permissions/*/autogenerated/` do crate), nunca de memória. Foi assim que os
da janela `splash` foram escolhidos (§5.2 do processo).

## 5. Atualização: cada plataforma tem o seu caminho

O updater do Tauri (minisign + `/api/updates`) é **só desktop**. No celular:

- **Android fora da Play**: o app mostra um card "Baixar atualização" que abre
  `streamz.chat/download` no navegador. A versão nova é consultada pela mesma
  rota `/api/updates`, com target `android`.
- **Android na Play** e **iOS na App Store**: quem atualiza é a loja.

Nada disso reaproveita a janela `splash`, e é por isso que ela sai da config do
celular (§2).

## 6. A web precisa saber que está num celular

`apps/web/hooks/useEhMobile.ts` responde "isto é um celular?" por
`(max-width: 767px), (pointer: coarse) and (max-height: 599px)` — e hoje
devolve **`false` sempre que `isTauri()`**. Isso foi escrito para o desktop: a
janela do Windows pode ser arrastada para menos de 768px de largura e virar
barra de abas ali seria uma regressão do produto instalado.

No Tauri **Android e iOS** a resposta tem que ser **`true`**. A correção é por
plataforma, não por tamanho: dentro do Tauri, decidir pelo `platform()` do
`@tauri-apps/plugin-os` (ou pelo `navigator.userAgent`, se preferir não
acrescentar dependência) — `android`/`ios` → mobile; `windows`/`linux`/`macos`
→ continua exatamente como está hoje. Fora do Tauri, nada muda: vale a consulta
de mídia.

A parte que decide fica **pura e testada**, com casos para: Tauri desktop
(`false`), Tauri Android (`true`), Tauri iOS (`true`), navegador estreito
(`true`), navegador largo (`false`). Dono: **Bloco 2**.
